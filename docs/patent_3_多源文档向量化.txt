                        专利交底书
================================================================================

【发明名称】
一种面向多源异构文档的统一语义向量化与跨格式知识检索方法

【技术领域】
本发明涉及文档处理与自然语言处理技术领域，具体涉及一种将多种异构
格式（办公文档、网页、源代码、标记文本）统一转换为语义向量并纳入
同一检索空间的方法，实现跨格式的知识库构建与智能问答。

【背景技术】
企业知识管理场景中，知识资产通常以多种异构格式分散存储，包括但不限于：
Word 技术规范 (.docx)、PPT 培训材料 (.pptx)、PDF 手册 (.pdf)、
HTML 网页 (.html)、C/C++/Java 源代码 (.c/.java/.cpp)、Markdown 文档 (.md)、
纯文本 (.txt) 等。

现有方案的不足：
1) 格式孤岛：不同格式需使用不同工具查看和检索，无法跨格式统一查询；
2) 解析器碎片化：各格式需单独配置解析器，缺乏统一的内容提取流水线；
3) 元数据丢失：格式转换过程中源文件类型、路径、标题等上下文信息丢失，
   导致检索结果缺乏可追溯性；
4) 编码兼容性差：对中文 Windows 环境下的 GBK/GB2312 编码源码文件
   缺乏自动探测能力，导致乱码或加载失败；
5) 结构化信息浪费：Word/PPT 中的表格、PPT 中的幻灯片层级结构在纯文本
   转换时被丢弃，影响检索精度。

【发明内容】
本发明提出一种多源异构文档统一语义向量化流水线，核心思想是：建立
统一的"格式路由→内容提取→分块→向量化"处理链，每种格式配备专用
解析器，但输出统一的 DocumentChunk 数据结构，最终汇入同一向量空间
供语义检索。

技术方案包括以下步骤：

S1）格式路由层：
    系统维护一个可扩展的格式后缀映射表 SUPPORTED_EXTENSIONS，
    涵盖 Markdown(.md)、文本(.txt)、PDF(.pdf)、Word(.docx)、
    PowerPoint(.pptx)、HTML(.html/.htm)、
    C/C++ 源码(.c/.cc/.cpp/.cxx/.h/.hpp/.hxx)、Java(.java)。
    根据文件后缀自动路由到对应的解析器。

S2）多格式解析器矩阵：
    - PDF 解析器：基于 pymupdf 逐页提取文本，保留页序；
    - Word 解析器：基于 python-docx 提取段落文本 + 表格内容，
      表格按 " | " 分隔符格式化为可检索的行文本；
    - PPT 解析器：基于 python-pptx 逐页提取幻灯片文本 + 表格，
      保留 "[幻灯片 N]" 层级标记；
    - HTML 解析器：基于 BeautifulSoup 剥离 script/style 标签后
      提取纯文本，保留换行结构；
    - 源码解析器：针对 C/C++/Java 等源码文件，自动探测编码
      （UTF-8 → GBK → GB2312 → GB18030 → latin-1 依序尝试），
      解决中文 Windows 环境下的编码兼容问题；

S3）统一分块与元数据保留：
    所有解析器输出的文本汇入统一的分块流水线：
    - Markdown 按 ## 二级标题优先切分；
    - 代码块（``` ```）保持完整不截断；
    - 超长段落按段落边界再切分，支持 overlap 重叠；
    每个分块附加完整元数据：
      {source: 相对路径, title: 文档标题, chunk_index: 分块序号,
       file_type: 原始格式后缀}

S4）统一向量化入库：
    所有分块通过同一 embedding 模型（如 text2vec-base-chinese）
    向量化后存入 ChromaDB，metadata 保留原始格式信息，使检索结果
    可追溯到具体文件的第几个分块。

【有益效果】
1) 跨格式统一检索：用户在单一查询界面即可检索所有格式的知识资产，
   一次提问可同时命中 Word 规范、PPT 培训材料和源码注释；
2) 格式可扩展：新增格式仅需添加解析器函数 + 注册后缀，架构无需改动；
3) 编码自适应：中文 Windows 环境下的 GBK 编码源码零配置自动识别；
4) 结构信息保留：表格、幻灯片层级等结构化信息以文本形式保留在分块中，
   LLM 可利用这些信息生成更精确的回答；
5) 来源可追溯：每个检索结果精确标注来源文件路径、格式类型和分块位置。

【具体实施方式】
以"诊断软件智能问答系统"为例：

知识库目录结构：
  knowledge/
    ├── specs/
    │   ├── OBD-II协议规范.docx       ← 表格密集型文档
    │   └── 培训课件.pptx              ← 幻灯片
    ├── manuals/
    │   └── 用户手册.pdf               ← 扫描件文本
    ├── webhelp/
    │   └── 故障码查询.html            ← HTML 帮助页面
    └── src/
        ├── obd_parser.c               ← C 源码 (GBK 编码)
        └── diagnotic_service.java     ← Java 源码 (UTF-8)

处理流程：
步骤 1：扫描目录 → 识别 6 个文件 × 5 种格式；
步骤 2：路由分发：
  - .docx → Word 解析器 → 提取 45 段文本 + 12 个表格行；
  - .pptx → PPT 解析器 → 提取 20 张幻灯片文本；
  - .pdf  → PDF 解析器 → 提取 80 页文本；
  - .html → HTML 解析器 → 剥离标签提取纯文本；
  - .c    → 源码解析器 → 自动探测 GBK 编码解码；
  - .java → 源码解析器 → UTF-8 解码；
步骤 3：统一分块 → 共产生 234 个文档块；
步骤 4：向量化入库 → 234 个分块写入 ChromaDB。

用户查询 "OBD-II P0135 故障码" → 检索结果：
  result[0]: 来自 [specs/OBD-II协议规范.docx] 表格行（distance=0.32）
  result[1]: 来自 [src/obd_parser.c] 源码注释（distance=0.45）
  result[2]: 来自 [webhelp/故障码查询.html] 正文（distance=0.51）
