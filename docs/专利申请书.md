## 一、一种面向技术文档的多级混合检索与可信生成方法

**对应代码**：[`rag/chain.py::_retrieve()`](../rag/chain.py#L277) · [`_rerank()`](../rag/chain.py#L351) · [`query_stream_with_status()`](../rag/chain.py#L502)

### 1.1 技术领域

本发明涉及自然语言处理和智能问答领域，具体涉及一种面向 API 技术文档的多级混合检索、重排序与可信生成方法。

### 1.2 背景技术

现有 RAG（检索增强生成）系统通常采用单一的向量检索或关键词检索方案。向量检索擅长语义匹配但对精确关键词（如 API 函数名、类名）不敏感；BM25 关键词检索擅长精确匹配但缺乏语义理解。此外，LLM 生成答案时可能出现"幻觉"——回答内容表面上合理但实际并非来自知识库。

### 1.3 技术方案

本发明提出一种**三级递进式混合检索与可信生成 pipeline**：

```
用户问题
  │
  ├─ [1] 向量检索（语义粗筛）
  │     └─ 候选集扩大至 top_k × 3，为融合提供更多候选
  │
  ├─ [2] BM25 关键词检索（精确补位）
  │     └─ 自研 jieba 中文分词 BM25 引擎
  │     └─ 复用内存缓存 corpus，避免重复查 ChromaDB
  │
  ├─ [3] RRF 递归排序融合
  │     └─ 内容哈希去重（避免同一文档在不同检索源重复计分）
  │     └─ RRF_score(d) = Σ 1/(k + rank_i(d))
  │     └─ 融合结果不足 top_k 时 BM25 补位
  │
  ├─ [4] BM25 兜底机制
  │     └─ 向量检索零结果时自动降级为纯 BM25 检索
  │
  ├─ [5] Cross-Encoder Reranker 精排
  │     └─ 对前 top_n 候选文档进行 query-doc pair 精细打分
  │     └─ 类级别模型缓存，多用户复用
  │     └─ 熔断器：加载失败后标记跳过，避免反复超时
  │
  ├─ [6] LLM 生成（带可信度校验）
  │     └─ 上下文自适应 token 预算管理
  │     └─ 低置信度提醒注入
  │     └─ 双重校验（见专利二）
  │
  └─ 输出
```

### 1.4 有益效果

| 对比项 | 传统方案 | 本发明 |
|--------|---------|--------|
| API 函数名匹配 | 向量检索易遗漏 | BM25 关键词精确命中 |
| 语义理解 | 关键词检索无语义 | 向量检索 + Reranker 语义精排 |
| 多源结果融合 | 简单拼接/加权 | RRF 去重融合 + BM25 补位 |
| 极端情况 | 零结果静默失败 | BM25 自动兜底 |
| 模型加载 | 每次查询加载 | 类级别缓存 + 熔断保护 |

## 二、一种大语言模型生成内容的可信度双重校验方法

**对应代码**：[`rag/chain.py::query_stream_with_status()`](../rag/chain.py#L603-L619)

### 2.1 技术领域

本发明涉及人工智能安全领域，具体涉及一种对 RAG 系统中大语言模型生成答案的可信度进行程序化双重校验的方法。

### 2.2 背景技术

大语言模型存在"幻觉"问题：当知识库无相关内容时，模型可能编造看似合理的回答。现有方案主要依赖 prompt 约束（如"仅基于知识库回答"），但 LLM 不总是遵守约束。

### 2.3 技术方案

本发明采用 **prompt 约束 + 后处理程序化校验** 的双层保障机制：

```
第一层：Prompt 格式约束
  ├─ 强制要求以【知识库回答】或【拒绝回答】开头
  ├─ 低置信度（top_distance > 阈值）时注入 ⚠️ 强提醒
  │   内容示例：
  │   "⚠️ 以下知识库内容与问题的相关性较低。
  │    如果内容确实无关，必须回复「拒绝回答」，
  │    绝对不要自行回答！"
  └─ 约束 LLM 仅基于知识库上下文回答

第二层：后处理来源校验
  ├─ 检查回答是否以【知识库回答】/【拒绝回答】开头
  ├─ 检查回答中是否包含检索来源文件名
  │   遍历 sources 列表，逐一匹配 source name
  ├─ 正则匹配 "来源/source: xxx.md/cc/h" 文件引用模式
  └─ 双重校验均失败 → 自动替换为：
      "抱歉，知识库中暂无相关内容，无法回答该问题。"
```

### 2.4 有益效果

- **Prompt 约束**：从源头引导 LLM 按格式输出
- **后处理校验**：即使 LLM 不遵守格式，只要引用了知识库来源文件名也算通过
- **自动拦截**：零人工干预，幻觉回答被程序化拦截
- **低置信度提醒**：在上下文最前方插入强提示，强化 LLM 的自查意识

## 三、一种面向源代码文档的知识库构建与智能分块方法

**对应代码**：[`rag/loader.py::_split_by_headers()`](../rag/loader.py#L33) · [`_read_text_file()`](../rag/loader.py#L129)

### 3.1 技术领域

本发明涉及文档处理和知识库构建领域，具体涉及一种针对 C/C++ 源代码及 Markdown 技术文档的智能分块与编码自适应方法。

### 3.2 背景技术

技术文档知识库中常混有 C/C++ 源码文件（.c/.cc/.cpp/.h/.hpp）。传统分块方法存在以下问题：
- 代码块被从中间截断，破坏语法完整性
- 中文 Windows 环境源码编码多样（GBK/GB2312/UTF-8），单一编码读取导致乱码
- 分块重叠区可能跨越代码块边界

### 3.3 技术方案

**（1）代码块保护的两遍分块算法**

```
第一遍：按 Markdown 标题切分
  └─ 追踪 ``` 代码块边界
  └─ 代码块内不切分（即使遇到 ## 标题）
  └─ 每个 section 携带原始标题作为上下文

第二遍：超长 section 按段落切分
  └─ 再次追踪 ``` 代码块边界
  └─ 代码块内的段落不单独切分（保持完整）
  └─ 在非代码块区域按 \n\n 段落边界切分
  └─ 分块重叠区不跨越代码块边界
```

**（2）中文 Windows 源码多编码自动探测**

```
编码探测链（优先级降序）：
  utf-8  →  gbk  →  gb2312  →  gb18030  →  latin-1
    ↓          ↓         ↓          ↓           ↓
  标准      中文      中文      中文扩展     西欧兜底
  Unicode   Windows   国标      国标扩展     (无失败)
```

每种编码尝试解码，首个成功即采用。最终兜底 utf-8 + errors=replace（永不会失败）。

**（3）支持的文档格式**

| 类型 | 扩展名 |
|------|--------|
| 文档 | `.md`, `.txt`, `.pdf` |
| C/C++ 源文件 | `.c`, `.cc`, `.cpp`, `.cxx` |
| C/C++ 头文件 | `.h`, `.hpp`, `.hxx` |

### 3.4 有益效果

- **代码块完整性**：API 示例代码不被截断，LLM 可获取完整代码片段
- **中文兼容性**：自动适配 GBK/GB2312 编码的中文注释源码
- **元数据高效提取**：文件列表仅读前 2000 字节提取标题，不加载全文

## 四、一种基于分词器版本的倒排索引自动重建方法

**对应代码**：[`rag/chain.py::_ensure_bm25_ready()`](../rag/chain.py#L224) · [`BM25Retriever`](../rag/chain.py#L33)

### 4.1 技术领域

本发明涉及信息检索领域，具体涉及一种 BM25 倒排索引的版本感知式自动维护方法。

### 4.2 背景技术

BM25 倒排索引构建后，当文档库更新或分词逻辑升级时，索引数据会过期。传统方案需要手动重建或在每次查询时全量重建（性能差）。

### 4.3 技术方案

```
自动重建判断三元组：
  ├─ 索引是否为空（首次使用）
  ├─ 向量库文档数是否变化（current_count ≠ last_doc_count）
  └─ 分词器版本号是否变化（TOKENIZER_VERSION 常量）

触发条件：任一条件为真 → 自动重建索引

实现细节：
  ├─ 延迟初始化：首次 _retrieve() 时才构建，避免启动耗时
  ├─ 内存缓存：BM25 corpus 缓存于 _corpus 属性，搜索时直接复用
  │   无需每次查询都从 ChromaDB 全量加载文档
  └─ 版本感知：分词逻辑优化后仅需递增 TOKENIZER_VERSION
```

### 4.4 有益效果

| 对比项 | 传统方案 | 本发明 |
|--------|---------|--------|
| 索引更新 | 手动重建 | 自动检测并重建 |
| 分词升级 | 无法感知 | 版本号变化自动触发 |
| 启动速度 | 构建索引耗时 | 延迟初始化 |
| 查询性能 | 每次查 ChromaDB | 内存缓存直接检索 |

## 五、一种离线知识库系统 AI 模型的检测、加载与熔断方法

**对应代码**：[`rag/config.py::detect_local_models()`](../rag/config.py#L47) · [`rag/chain.py::_rerank()`](../rag/chain.py#L371-L406)

### 5.1 技术领域

本发明涉及深度学习模型部署领域，具体涉及一种离线环境中 AI 模型的自适应路径检测、完整性校验与故障熔断方法。

### 5.2 背景技术

离线部署场景中，AI 模型（Embedding、Reranker）的存储布局不统一：可能是扁平目录，也可能是 HuggingFace 缓存格式（`models--org--name/snapshots/<hash>/`）。传统方案难以自动适配多种布局，且模型加载失败会导致每次查询都超时等待。

### 5.3 技术方案

**（1）双路径自适应检测**

```
检测优先级：扁平目录 > HF 缓存最新 snapshot

扁平目录检测：
  └─ model/text2vec-base-chinese/config.json 存在？

HF 缓存检测：
  └─ model/models--shibing624--text2vec-base-chinese/snapshots/
      └─ 按 mtime 排序取最新 snapshot
      └─ 校验：config.json + 模型权重文件（.safetensors / .bin / .h5）
        均存在 → 设置环境变量，启用 local_files_only 模式
```

**（2）类级别缓存与故障熔断**

```
RAGChain 类级别状态：
  ├─ _reranker_model: 模型实例单例缓存
  ├─ _reranker_model_name: 缓存对应的模型标识
  └─ _reranker_load_failed: 加载失败标记

熔断逻辑：
  ├─ 远程加载失败 → 设置 _reranker_load_failed = True
  ├─ 后续查询 → 跳过加载，直接返回未排序结果
  ├─ 模型名称变更 → 自动清除熔断标记，允许重试
  └─ 本地路径加载永不触发熔断（本地失败应报错）
```

**（3）入口无关的模型检测**

检测函数 [`detect_local_models()`](../rag/config.py#L47) 同时被 `run_app.py` 和 `app.py` 调用，无论用户通过 `run_app.py` 启动还是 `streamlit run app.py` 启动，模型检测均可正常工作。幂等调用，已有环境变量时不覆盖。

### 5.4 有益效果

- **布局兼容**：自动适配扁平目录和 HF 缓存两种存储格式
- **完整性校验**：不仅检查目录存在，还验证 config.json + 权重文件
- **故障熔断**：远程加载失败后不反复重试，避免每次查询都超时
- **入口无关**：两种启动方式均可靠检测

## 六、一种大语言模型流式服务的高可用降级与重试方法

**对应代码**：[`rag/chain.py::_call_llm_stream()`](../rag/chain.py#L633) · [`_call_llm_nonstream()`](../rag/chain.py#L675)

### 6.1 技术领域

本发明涉及云计算和大语言模型调用领域，具体涉及一种 LLM 流式调用的自适应降级与指数退避重试方法。

### 6.2 技术方案

```
调用策略：
  ├─ 优先流式调用（实时 token 级展示，用户体验最优）
  ├─ 流式失败 → 自动降级为非流式（兼容性兜底）
  └─ 均失败 → 返回结构化错误信息

重试策略（指数退避）：
  ├─ 最多重试 3 次
  ├─ 间隔：2^attempt 秒（1s → 2s → 4s）
  └─ 每次重试均包含完整 message 上下文

空响应检测：
  ├─ 流式：遍历完所有 chunk 后 has_content = False → 触发重试
  └─ 非流式：content 为空 → 触发重试

错误信息：
  └─ 包含模型名 + 错误详情 + 审计日志
```

### 6.3 降级链路

```
                        ┌─ 成功 → 流式输出
流式调用 ──失败──→ 非流式调用 ─┬─ 成功 → 全文输出
                                └─ 失败 → 结构化错误
                                              ├─ 模型名
                                              ├─ 错误详情
                                              └─ 审计日志记录
```

### 6.4 有益效果

- **高可用**：流式不可用时自动降级，保证服务连续性
- **用户体验**：流式优先保证 token 级实时展示
- **智能重试**：指数退避避免频繁请求触发限流
- **可观测性**：每次失败均记录审计日志
